Part 1 · The production world¶

Simulate the rideshare traffic¶

We continue with the Gujarat rideshare app from Lab Evaluation 2. For every ride the app predicts whether the rider will tip (tipped = 1), so it can decide when to show the tip screen.

simulate_rides(n, week, seed) generates one week of ride requests. From week 4 the monsoon arrives: more people take cabs for long trips, waits get longer and surge pricing becomes common. The monsoon(week) intensity ramps from 0 to 1 over weeks 4–7 and then stays at 1.

The rule that decides whether a rider tips, tip_probability(...), never changes. Only the mix of inputs changes. This is covariate shift.

Kind of shift What changes Example in this app
Covariate shift $P(x)$ changes, $P(y \mid x)$ stays the same Monsoon → many more long rides
Label (prior) shift $P(y)$ changes, $P(x \mid y)$ stays the same Festival week → everyone tips more
Concept drift $P(y \mid x)$ changes A redesigned tip screen changes rider behaviour

FEATURES = ["distance_km", "fare", "wait_min", "surge", "hour", "driver_rating"]
TARGET = "tipped"

def monsoon(week):
    """Monsoon intensity: 0 up to week 3, ramps up over weeks 4-7, then stays at 1."""
    return float(np.clip((week - 3) / 4, 0, 1))

def tip_probability(distance, wait, surge, hour, rating):
    """The 'true' tipping rule of riders. It does NOT depend on the week."""
    evening = ((hour >= 18) | (hour <= 2)).astype(float)
    rush = ((hour >= 8) & (hour <= 10)).astype(float)
    logit = (-0.3 + 1.5 * (rating - 4.3) / 0.4 - 0.12 * (wait - 7)
             + 0.30 * (distance - 5) - 0.12 * np.maximum(distance - 13, 0) ** 2
             + 1.3 * evening - 1.6 * rush - 0.4 * surge)
    return 1 / (1 + np.exp(-logit))

def simulate_rides(n, week=0, seed=0, season=None):
    """One week of ride requests. `season` overrides monsoon(week) if given (0..1)."""
    rng = np.random.default_rng(seed)
    m = monsoon(week) if season is None else season
    distance = np.round(rng.gamma(2.2, 1.8 * (1 + 2.0 * m), n) + 0.5, 2)
    surge = rng.binomial(1, 0.20 + 0.40 * m, n)
    fare = np.round(25 + 12 * distance * (1 + 0.5 * surge) + rng.normal(0, 8, n), 2)
    wait = np.round(rng.gamma(2.0, 3.0 * (1 + 0.5 * m), n) + 1, 1)
    hour = rng.integers(0, 24, n)
    rating = np.round(np.clip(rng.normal(4.3, 0.4, n), 2.5, 5.0), 1)
    tipped = rng.binomial(1, tip_probability(distance, wait, surge, hour, rating))
    return pd.DataFrame({
        "request_id": [f"W{week:02d}-{seed}-{i:05d}" for i in range(n)],
        "user_id": rng.integers(1, 5001, n), "week": week,
        "distance_km": distance, "fare": fare, "wait_min": wait, "surge": surge,
        "hour": hour, "driver_rating": rating, TARGET: tipped})

  • default_rng creates an independent random generator. The same seed always gives the same "week" of data, regardless of what other cells ran before. That is why the lab passes a different seed for every simulated week.
  • np.maximum(distance - 13, 0) works element by element: it is 0 for rides up to 13 km and grows for longer rides. Long rides (≥ 13 km) are flat-fare intercity trips, where tips drop sharply. Remember this; it matters in Part 4.

Keep models in a model registry¶

This is the Lab 6 idea in miniature. Every version gets a folder holding model.joblib and a model_card.json. One file, registry.json, records which version is in production and keeps a history of every promotion and rollback.

A redeployment then means changing one pointer, and a rollback means changing it back.

In [6]:
REGISTRY = ARTIFACTS / "registry"

def register_model(model, version, metrics, train_weeks, notes=""):
    folder = REGISTRY / version
    folder.mkdir(parents=True, exist_ok=True)
    joblib.dump(model, folder / "model.joblib")
    card = {"version": version, "model_class": type(model).__name__, "features": FEATURES,
            "train_weeks": train_weeks, "metrics": metrics, "notes": notes,
            "registered_at": time.strftime("%Y-%m-%d %H:%M:%S")}
    (folder / "model_card.json").write_text(json.dumps(card, indent=2))
    return card

def load_model(version):
    return joblib.load(REGISTRY / version / "model.joblib")

def read_registry():
    path = REGISTRY / "registry.json"
    return json.loads(path.read_text()) if path.exists() else {"production": None, "history": []}

def set_production(version, reason):
    reg = read_registry()
    reg["history"].append({"time": time.strftime("%H:%M:%S"), "from": reg["production"],
                           "to": version, "reason": reason})
    reg["production"] = version
    (REGISTRY / "registry.json").write_text(json.dumps(reg, indent=2))
    return reg

Route traffic between models¶

A router decides which model answers each request. For experiments, the assignment must be:

  • random, so the two groups are comparable,
  • sticky, so the same user always sees the same model (otherwise one rider gets a mix of both experiences),
  • independent across experiments, so being in the treatment group of one test says nothing about the next.

Hashing the user id with an experiment-specific salt gives all three properties without storing a lookup table.

In [7]:
def bucket(user_id, salt):
    """Stable pseudo-random bucket 0..99 for a user within one experiment."""
    digest = hashlib.md5(f"{salt}:{user_id}".encode()).hexdigest()
    return int(digest[:8], 16) % 100

class Router:
    def __init__(self, control_version, candidate_version=None, candidate_pct=0, salt="exp"):
        self.control_version = control_version
        self.candidate_version = candidate_version
        self.candidate_pct = candidate_pct
        self.salt = salt
        self.models = {"control": load_model(control_version)}
        if candidate_version is not None:
            self.models["candidate"] = load_model(candidate_version)

    def assign(self, user_id):
        if self.candidate_version is not None and bucket(user_id, self.salt) < self.candidate_pct:
            return "candidate"
        return "control"

    def serve(self, requests):
        """Predict for a batch of requests; returns a prediction log (no labels yet)."""
        log = requests[["request_id", "user_id", "week"]].copy()
        log["variant"] = [self.assign(u) for u in requests["user_id"]]
        log["model_version"] = log["variant"].map({"control": self.control_version,
                                                   "candidate": self.candidate_version})
        log["prediction"] = -1
        for variant, model in self.models.items():
            mask = (log["variant"] == variant).to_numpy()
            if mask.any():
                log.loc[mask, "prediction"] = model.predict(requests.loc[mask, FEATURES])
        return log

def attach_outcomes(log, requests):
    """Labels arrive later (after the ride). Join them to the prediction log."""
    out = log.merge(requests[["request_id", TARGET]], on="request_id")
    out["correct"] = (out["prediction"] == out[TARGET]).astype(int)
    return out

def summarize(log):
    return log.groupby("variant").agg(requests=("request_id", "size"), users=("user_id", "nunique"),
                                      accuracy=("correct", "mean")).round(4)

Syntax clarity: hashlib.md5(...).hexdigest() and int(x, 16)

  • f"{salt}:{user_id}".encode() turns the string into bytes, and md5 hashes them. The same input always gives the same 32-character hex string, and a tiny change (a different salt) gives an unrelated one.
  • int(digest[:8], 16) reads the first 8 hex characters as a base-16 integer (0 to about 4.3 billion), and % 100 maps it to a bucket from 0 to 99. A user goes to the candidate when bucket < candidate_pct.
  • MD5 is fine here because we need speed and uniformity, not security.

Part 2 · A/B testing a new model¶

Offline, v2 beats v1 by about 4 percentage points. Offline is not online: the validation set could be stale, the serving code could differ, and real users could react differently. An A/B test settles the question on live traffic.

Step What you do
1 Fix the hypothesis and one primary metric before starting (here: prediction accuracy, the share of correct tip predictions)
2 Compute the sample size needed to detect the smallest difference you care about
3 Split traffic randomly and stickily between control (A) and candidate (B)
4 Run until the planned sample size is reached. Do not stop early because the numbers look good
5 Test significance and report a confidence interval
6 Decide: ship, do not ship, or extend the test

Is the difference real?¶

Each prediction is either correct or not, so each variant has a proportion of correct predictions: $\hat p_A = x_A/n_A$ and $\hat p_B = x_B/n_B$. The two-proportion z-test asks whether the gap could be just noise.

$$\hat p = \frac{x_A + x_B}{n_A + n_B}, \qquad z = \frac{\hat p_B - \hat p_A}{\sqrt{\hat p(1-\hat p)\left(\frac{1}{n_A} + \frac{1}{n_B}\right)}}, \qquad \text{p-value} = 2\,\big(1 - \Phi(|z|)\big)$$

The 95% confidence interval for the difference uses the unpooled standard error:

$$(\hat p_B - \hat p_A) \pm 1.96\sqrt{\frac{\hat p_A(1-\hat p_A)}{n_A} + \frac{\hat p_B(1-\hat p_B)}{n_B}}$$

$\Phi$ is the standard normal CDF: stats.norm.cdf. A small p-value (< α = 0.05) means a gap this large would be unlikely if the models were equally good.

Part 3 · Safe redeployment¶

Winning an A/B test does not make the rollout safe. The new model still has to be deployed without hurting users if something breaks.

Strategy How it works Rollback
Big-bang Replace the old model for 100% of traffic at once Slow and painful
Blue–green Run old (blue) and new (green) side by side, then switch the router Flip the pointer back
Shadow (dark launch) New model sees real traffic, but its predictions are only logged, never used Nothing to roll back
Canary Send 5% → 25% → 50% → 100% of traffic, checking guardrail metrics at each stage Automatic, at the failing stage

The registry's production pointer and the router's candidate_pct are all we need for blue–green, canary and rollback.

Shadow-deploy a buggy model¶

A teammate retrained the model and registered it as v3. Offline it looks great. However, the new serving code sends the features in the wrong order. That kind of bug never shows up in an offline notebook evaluation.

A shadow deployment runs v3 on real requests next to production and compares the two sets of predictions before any user sees them.

In [ ]:
class ColumnOrderBug:
    """Wraps a model; simulates serving code that sends the features in reverse order."""
    def __init__(self, model):
        self.model = model
    def predict(self, X):
        X_bad = X[FEATURES[::-1]].copy()
        X_bad.columns = FEATURES          # same column names, wrong values!
        return self.model.predict(X_bad)

v3_core = HistGradientBoostingClassifier(max_depth=4, learning_rate=0.05, max_iter=300,
                                         random_state=SEED).fit(fit_df[FEATURES], fit_df[TARGET])
v3_offline = accuracy_score(val_df[TARGET], v3_core.predict(val_df[FEATURES]))
register_model(ColumnOrderBug(v3_core), "v3", {"offline_val_acc": round(v3_offline, 4)}, [0],
               "deeper boosting (serving code has a column-order bug)")
print("v3 offline validation accuracy (evaluated WITHOUT the serving bug):", round(v3_offline, 4))

def shadow_compare(prod_version, shadow_version, requests):
    prod, shadow = load_model(prod_version), load_model(shadow_version)
    t0 = time.perf_counter(); p = prod.predict(requests[FEATURES]); t_prod = time.perf_counter() - t0
    t0 = time.perf_counter(); s = shadow.predict(requests[FEATURES]); t_shadow = time.perf_counter() - t0
    return {"agreement": float(np.mean(p == s)),
            "prod_ms_per_1k": 1000 * t_prod / len(requests) * 1000,
            "shadow_ms_per_1k": 1000 * t_shadow / len(requests) * 1000,
            "prod_acc_after_labels": accuracy_score(requests[TARGET], p),
            "shadow_acc_after_labels": accuracy_score(requests[TARGET], s)}

reqs = simulate_rides(4000, week=3, seed=301)
display(pd.DataFrame([{"shadow": "v2", **shadow_compare("v1", "v2", reqs)},
                      {"shadow": "v3", **shadow_compare("v1", "v3", reqs)}]).round(4))

v2 agrees with production on most requests, as expected for a slightly better model. v3 disagrees far more often, which is a red flag even before labels arrive. In a real system, a sudden drop in agreement or a jump in the share of one predicted class is a cheap and fast alarm.

Shadow mode needs no user exposure, but it doubles compute and cannot measure effects that depend on users seeing the prediction. A canary measures real outcomes on a small slice of users.

Compare distributions with a two-sample test¶

The Kolmogorov–Smirnov (KS) test compares two samples of one feature. Its statistic is the largest gap between the two empirical CDFs, from 0 (identical) to 1 (no overlap).

In [ ]:
ks_rows = []
for f in FEATURES:
    for w in [1, 8]:
        res = stats.ks_2samp(train_df[f], WEEK_DATA[w][f])
        ks_rows.append({"feature": f, "week": w, "ks_stat": res.statistic, "p_value": res.pvalue})
display(pd.DataFrame(ks_rows).pivot(index="feature", columns="week", values=["ks_stat", "p_value"]).round(4))

With thousands of rows, KS p-values become tiny even for harmless differences. A p-value tells you whether there is any difference, not how big it is. Production monitors therefore also track an effect size. The most common one in industry is the Population Stability Index (PSI):

$$\text{PSI} = \sum_{i=1}^{B} (c_i - r_i)\,\ln\frac{c_i}{r_i}$$

Here $r_i$ and $c_i$ are the fractions of the reference (training) and current data that fall in bin $i$. The bins are the deciles of the reference data. Rule of thumb: < 0.1 stable · 0.1–0.25 moderate shift · > 0.25 major shift.

Importance weighting. Under covariate shift, $P(y \mid x)$ is unchanged, so training rows are still correct, just in the wrong proportions. Weight every training row by

$$w(x) = \frac{p_{\text{prod}}(x)}{p_{\text{train}}(x)} \;\approx\; \frac{P(\text{prod} \mid x)}{1 - P(\text{prod} \mid x)} \cdot \frac{n_{\text{train}}}{n_{\text{prod}}}$$

using the domain classifier from TODO 6. Most scikit-learn models accept these weights through fit(X, y, sample_weight=w).

Automate retraining¶

Real systems do not retrain by hand. A retraining policy decides when to retrain. A champion/challenger gate decides whether the retrained model (challenger) actually replaces the current one (champion).

run_policy(policy) below simulates weeks 1–11:

  1. Serve the week's traffic with the current model and record its accuracy and max_psi (against the model's own training data).
  2. At the end of the week, the labels arrive.
  3. If policy(week, log) returns True, train a challenger on the last window weeks of labeled data. Hold out 30% of the newest week, and promote the challenger only if it is at least as accurate as the champion on that holdout.

Two simple policies are provided: never and every_4_weeks. If TODO 5 is not finished yet, max_psi will appear as NaN.

In [ ]:
def run_policy(policy, weeks=range(1, 12), window=2, week_data=None, label_delay=0):
    week_data = WEEK_DATA if week_data is None else week_data
    model = make_v2().fit(train_df[FEATURES], train_df[TARGET])
    reference = train_df[FEATURES]
    labeled = {0: train_df}
    log = []
    for week in weeks:
        reqs = week_data[week]
        try:
            max_psi = max(psi(reference[f], reqs[f]) for f in FEATURES)
        except NotImplementedError:
            max_psi = np.nan
        row = {"week": week, "accuracy": accuracy_score(reqs[TARGET], model.predict(reqs[FEATURES])),
               "max_psi": max_psi, "retrained": False, "promoted": False}
        log.append(row)
        if week - label_delay >= 1:                       # labels of (week - delay) arrive now
            labeled[week - label_delay] = week_data[week - label_delay]
        if policy(week, pd.DataFrame(log)):
            row["retrained"] = True
            newest = max(labeled)
            holdout = labeled[newest].sample(frac=0.3, random_state=week)
            recent = pd.concat([labeled[w] for w in sorted(labeled)[-window:]])
            recent = recent[~recent["request_id"].isin(holdout["request_id"])]
            challenger = make_v2().fit(recent[FEATURES], recent[TARGET])
            champ_acc = accuracy_score(holdout[TARGET], model.predict(holdout[FEATURES]))
            chall_acc = accuracy_score(holdout[TARGET], challenger.predict(holdout[FEATURES]))
            if chall_acc >= champ_acc:
                model, reference = challenger, recent[FEATURES]
                row["promoted"] = True
    return pd.DataFrame(log)

def never(week, log):
    return False

def every_4_weeks(week, log):
    return week % 4 == 0

def policy_summary(name, log):
    return {"policy": name, "mean_acc_w1_11": log["accuracy"].mean(),
            "mean_acc_w7_11": log.loc[log["week"] >= 7, "accuracy"].mean(),
            "retrains": int(log["retrained"].sum()), "promotions": int(log["promoted"].sum())}

logs = {"never": run_policy(never), "every_4_weeks": run_policy(every_4_weeks)}
display(logs["every_4_weeks"].round(3))
display(pd.DataFrame([policy_summary(k, v) for k, v in logs.items()]).round(4))

Syntax clarity: functions as arguments

run_policy(never) passes the function never itself, without calling it. Inside, policy(week, pd.DataFrame(log)) calls whichever function you passed. Any function with the signature (week, log) -> bool is a valid policy, so you can plug in new ones without changing run_policy.
